신규 고객을 찾기 전에 1분기로 자르면

작업 기록 · 2026년 10월 26–30일

2018년 1분기 결제액을 구할 때는 주문을 1분기로 잘라야 한다. 그런데 그 주문의 고객이 신규인지 판단할 때도 같은 필터를 먼저 적용하면, 2017년에 구매한 이력이 사라진다. 1주차에 만든 질문을 다시 읽으면서 이 두 기간을 분리했다. 3주차에는 질문에 업무 기준을 분명히 적는 일과, 그 기준을 적용할 계산 순서를 모델이 잡는 일을 나눠서 살펴봤다.

신규와 기존을 가르는 데 전체 이력이 필요했다

팀 리뷰를 받은 질문 중 하나는 2018년 1분기 신규·기존 고객의 총 결제액이었다. 처음에는 금액이 부풀려지지 않았는지 확인해 달라는 지시도 붙였다. 리뷰 뒤에는 검증 절차를 별도로 두고, 질문에서 반환할 값을 고유 고객 수·총 결제액·고객당 결제액으로 명시했다. 첫 구매 여부는 구매 시각으로 판단하고, 첫 구매를 찾는 이력과 결제액을 집계할 대상 주문 모두 배송 완료 상태로 맞췄다.

계산 순서를 확인하려고 정답 SQL의 각 단계에서 한 행이 무엇을 뜻하는지 적었다.

단계 계산 한 행의 단위
첫 구매 전체 배송 완료 주문에서 customer_unique_id별 첫 구매 시각을 찾는다 고객 한 명
대상 주문 2018년 1분기 주문을 골라 고객의 첫 구매 시각에 따라 신규·기존을 붙인다 주문 한 건
결제 합산 결제 테이블에서 주문별 합을 구해 대상 주문에 붙인다 주문 한 건
결과 그룹별 고유 고객 수, 총 결제액, 고객당 금액을 계산한다 신규 또는 기존 그룹 하나

예를 들어 배송을 마친 주문이 2017년과 2018년 2월에 한 건씩 있는 사람은 기존 고객이다. 2017년 주문으로 고객을 분류하고 2월 주문의 결제액을 기존 그룹에 더한다. 1분기를 먼저 자르면 두 번째 주문이 첫 주문처럼 보인다. 고객 키를 주문마다 발급되는 customer_id로 바꿔 계산해도 기존 고객이 0명이 됐다. 상품 테이블을 붙인 확인용 계산에서는 신규 그룹 결제액이 약 312만에서 402만으로 늘었다. 고객을 가르는 단계와 금액을 더하는 단계가 각자 다른 단위를 요구한다는 게 숫자로 드러났다.

정답 SQL과 별도 Python 계산은 신규 19,904명과 총 결제액 3,119,633.17, 기존 307명과 총 결제액 46,162.57로 일치했다. 20문항 평가에서 기본 모델이 생성한 SQL을 읽어 보니 고객 키, 전체 이력에서의 첫 구매, 주문별 결제 합산 기준은 들어 있었다. 실행은 10초 제한을 넘겼다. 어떤 계산이 병목인지는 그 실행 기록만으로 확인할 수 없었다.

재주문율은 고객별 기준 주문부터 정했다

다른 질문은 카테고리별 수령 후 30일 재주문율이었다. 초안에서는 수령 기간, 같은 카테고리 주문만 재주문으로 볼지, 한 고객의 수령 주문이 여럿이면 어느 주문을 기준으로 삼을지가 열려 있었다. 2017년과 2018년 모두 3~7월에 수령한 주문으로 기간을 맞췄다. 각 고객이 그 기간에 처음 받은 주문을 기준으로, 수령 시각보다 늦고 720시간 이내에 구매한 별도의 배송 완료 주문이 있는지 셌다. 재주문 쪽의 카테고리는 제한하지 않았다.

2018년 대상 고객이 50명 이상인 카테고리에서 가장 높은 값은 moveis_sala의 3/118명, 2.54%였다. 같은 카테고리의 2017년 값은 0/83명이었다. 최소 인원 조건을 풀었을 때는 1/27명이 재주문한 수입 서적 카테고리가 1위였다. 두 문항 모두 정답 SQL과 독립적으로 작성한 Python 계산을 대조했다. 이 비교를 하면서 무엇을 세는지뿐 아니라, 카테고리를 순위 후보에 넣는 기준도 정답의 일부라는 걸 확인했다.

질문은 그대로 두고 계획 호출을 넣었다

10월 27일에는 팀의 기존 실행기로 비교할 두 경로를 발표했다. 기준선인 E0는 질문, 문항 조건, 테이블 정의를 받아 SQL을 바로 쓴다. A3는 같은 입력으로 모델에 풀이 계획을 한 번 요청한 뒤, 원래 입력과 계획을 함께 보내 SQL을 받는다. 두 조건에 같은 SQL 생성 지시문을 썼다. 계획 호출에는 테이블, 조인 키, 필터, 집계 단위와 계산식, 정렬·개수 제한을 순서대로 적게 했다. SQLite에 실행되는 것은 두 번째 호출에서 나온 SQL 한 개다.

계획 한 줄이 실제 SQL의 어디로 가는지 보려고 2주차에 작성한 결제 수단별 총액 문항 bang-001의 예비 실행을 읽었다. 모델은 주문과 결제 테이블을 order_id로 연결하고, 2017년 구매 중 배송 완료를 골라 결제 수단별 합을 내겠다고 썼다. 생성 SQL에서 이 세 항목은 각각 JOIN, 기간과 상태를 거르는 WHERE, GROUP BY payment_type과 SUM으로 이어졌다. A3와 E0 모두 이 문항을 맞혔다. 계획과 SQL을 대응시켜 읽을 수 있다는 것까지 확인한 사례였다.

공부할 때는 ‘문제를 나눈다’는 말이 어느 단계의 동작인지 구분했다. Plan-and-Solve는 계획을 세워 풀이를 이어가는 구조를, Least-to-Most는 앞 하위 문제의 답을 다음 하위 문제에 넘기는 구조를 설명한다. DIN-SQL은 스키마 연결, 분류와 분해, SQL 생성, 자기 수정에 역할을 나눈다. 팀의 A3는 이 가운데 풀이 계획을 만드는 한 단계에 초점을 맞췄다. 덕분에 계획과 생성 SQL을 함께 저장해, 문항 조건이 어느 단계에서 빠졌는지 비교할 수 있었다. Plan-and-Solve · Least-to-Most · DIN-SQL

23개를 맞힌 두 조건에서 다른 문항이 틀렸다

초반에는 테이블과 열의 뜻을 설명하는 데이터 사전을 덧붙이는 B1-b도 시험했다. Olist v0.1의 네 문항 중 네 개가 실행됐고 세 개를 맞혔다. 이전 기준선도 같은 세 문항을 맞혔고 CLI 버전도 달라, 데이터 사전의 효과는 판단을 보류했다.

10월 30일에는 Olist v0.2의 같은 30문항으로 E0와 A3를 각 한 번 실행했다. 두 조건 모두 gpt-6-luna의 중간 추론 설정, Codex CLI 0.160.0, SQL 실행 제한 10초를 사용했다. 실행 정확도(EX)는 정답 SQL과 같은 결과를 낸 문항 수로 기록했다.

관측값 E0 A3
정답 23/30 23/30
실행 성공 26/30 25/30
모델 호출 30회 60회

A3에서는 세 문항을 새로 맞히고 세 문항을 새로 틀렸다. 매출 상위 판매자를 찾는 bird-012는 E0에서 반환 열 개수가 달랐고 A3에서 정답이 됐다. 반대로 kmk-001은 A3의 계획에서 한 해에만 등장한 카테고리도 포함하라는 조건이 빠졌다. 생성 SQL의 결과는 정답의 485행에 못 미치는 392행이었다. 계획이 빠뜨린 범위가 결과의 행 수로 드러난 사례다.

한 번의 실행에서는 문항별 변화가 다음에도 나타날지 알기 어려웠다. 4주차에는 같은 평가셋을 반복해 어떤 문항이 꾸준히 달라지는지 보고, 계획을 바꿀 때 SQL 지시문도 달라지면 두 변경을 어떻게 구분할지 따로 실험했다.
