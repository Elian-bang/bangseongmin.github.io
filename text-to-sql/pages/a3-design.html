E0에서 무엇을 바꿀까? 모델과 방법을 시험하고 A3를 고르기까지

작업 기록 · 2026년 10월 26–30일

3주차에는 팀의 기본 실행인 E0를 기준으로 A1~B4 중 각자 맡을 실험을 골랐다. E0는 질문, 문항 조건, 전체 스키마를 모델에 주고 SQL을 한 번 생성한 뒤 SQLite에서 실행해 정답과 비교한다. 2주차에 문항과 정답을 준비했다면, 이제는 같은 문항에 다른 모델을 쓰거나 입력과 생성 절차를 바꿨을 때 무엇이 달라지는지 볼 차례였다.

나는 처음부터 A3만 돌리지 않았다. Codex의 모델과 추론 강도를 바꾸고, Claude CLI와 Docker에서 돌린 로컬 모델도 시험했다. 예제, 데이터 사전, 실제 값, 지표 정의, 검색한 설명도 차례로 붙여 봤다. 각각을 돌려 보면서 모델이 바뀌어 답이 달라지는 경우, 질문의 기준이 모델에 전달되지 않은 경우, SQL이 제한 시간 안에 끝나지 않는 경우를 구분하게 됐다.

선택지마다 바꾸는 지점이 달랐다

당시 팀의 방법론 지도는 두 가지 질문으로 나뉘었다. 모델이 주어진 정보를 SQL로 잘 옮기는가, 그리고 모델이 DB의 테이블·값·업무 기준을 잘 이해하는가였다. 실험 하나를 맡아 평가셋과 채점 조건을 고정하고, E0에서 한 지점을 바꾸는 방식이었다.

실험 E0에서 바꾸는 지점 10월 26일 Olist v0.1 예비 정답
A1 · 모델 교체 SQL을 생성하는 모델을 바꾼다 3/4
A2 · 예제 질문과 SQL 예제를 입력에 붙인다 2/4
A3 · 문제 쪼개기 SQL을 쓰기 전에 풀이 계획을 한 번 생성한다 3/4
A4 · 여러 후보 SQL 후보 여러 개를 만들고 실행 결과를 보고 고른다 실행 기록 없음
B1 · 데이터 사전 테이블과 열의 의미를 설명한다 3/4
B2 · 값 예시 주문 상태나 결제 수단 같은 실제 값의 예를 준다 2/4
B3 · 지표 정의 매출, 신규 고객, 재주문의 계산 기준을 설명한다 2/4
B4 · 검색 질문과 관련된 사전 조각을 찾아 붙인다 2/4

A1은 Luna로 바꿔 실행했고, A2·A3와 B1~B4는 Sol로 실행했다. 당시 공유 E0는 Sol에서 3/4였다. 예비 실행의 Codex CLI는 0.163.0, 공유 E0의 CLI는 0.160.0이었다. 각 방법의 기록은 네 문항을 한 번씩 돌려 본 관찰이다. A4는 별도의 API 기준선이 필요한 선택지로 검토했다.

예를 들어 A2와 B2·B3·B4에서는 모두 hjy-001이 SQL 시간 초과로 실패했다. 예제를 주거나 입력의 설명을 늘린 뒤 점수가 떨어졌지만, 이 한 번의 결과로 예제나 설명이 오답을 만든다고 판단할 수는 없었다. 실패의 형태부터 따로 확인해야 했다.

모델과 추론 강도를 바꿔 봤다

같은 Olist v0.1의 SQL 네 문항에 다른 모델을 넣었다. Codex에서는 Luna로 바꾼 뒤 추론 강도도 바꿨고, Claude CLI에서는 Haiku와 Sonnet을, Docker에서는 Qwen2.5-Coder 7B를 실행했다.

실행 정답 실행 성공
공유 E0 · Codex Sol 3/4 4/4
Codex Luna · low / medium / high 3/4 · 3/4 · 2/4 모두 4/4
Claude CLI · Haiku 4/4 4/4
Claude CLI · Sonnet 2/4 3/4
Docker · Qwen2.5-Coder 7B 2/4 3/4

같은 hjy-001에서 Sonnet이 만든 SQL은 시간 초과했고, 로컬 Qwen은 SQLite 문법 오류가 났다. 두 실행은 정답 수가 같았지만 고쳐야 할 곳이 달랐다. 반대로 Haiku는 네 문항을 모두 맞혔다. 이 네 문항에서는 한 문제만 바뀌어도 점수가 25%p 움직이고, 실행 도구와 제공자 설정도 달랐다. 모델 순위를 정하기보다 어떤 실패가 관찰됐는지 읽는 데 이 결과를 썼다.

데이터 사전을 시험한 뒤, 풀이 순서를 살펴보기로 했다

10월 26일 진행 계획에서는 데이터 사전이 먼저 살펴볼 후보였다. 앞선 과제에서 customer_id와 customer_unique_id, 주문과 상품·결제의 행 단위를 혼동하면 결과가 달라지는 것을 확인했기 때문이다. 팀에서 B1을 맡은 사람이 있어, 나는 테이블과 열의 설명에 한 행의 뜻과 조인 규칙을 포함한 B1-b도 따로 돌렸다. 실제 상태 값 목록과 내 평가 문항의 함정을 알려 주는 문장은 덜어 냈다.

B1-b는 3/4로 공유 E0와 같은 문항을 맞혔다. 남은 hjy-002는 집계 수치는 맞았지만 카테고리명이 포르투갈어였다. 기대 결과는 영어였고, 모델 입력에는 영어로 반환하라는 조건이 없었다. 이 차이를 보면서 사전에 설명을 더하는 일과, 채점에서 요구하는 기준을 질문에 전달하는 일을 따로 봐야 했다.

같은 주에 팀 리뷰를 받은 재주문율과 신규·기존 고객 결제액 문항도 보완했다. 재주문율 문항은 두 해 모두 수령 후 30일을 관찰할 수 있도록 3~7월 수령으로 범위를 맞췄다. 결제액 문항은 전체 배송 완료 이력에서 고객의 첫 구매를 찾고, 결제액은 2018년 1분기 주문만 합산하도록 정리했다. 1분기로 먼저 자르면 2017년 구매 기록이 사라져 기존 고객도 신규처럼 보일 수 있었다. 업무 기준을 알아도 계산 순서가 달라지면 답이 달라지는 예였다.

10월 27일, A3로 비교할 두 경로를 발표했다

내가 맡은 A3에서는 모델이 먼저 사용할 테이블, 조인 키, 필터, 집계 단위와 계산식, 정렬·개수 제한을 글로 적는다. 두 번째 호출에서 원래 질문·문항 조건·스키마와 그 계획을 받아 SQL 하나를 만든다. 계획과 SQL이 각각 남기 때문에, 빠뜨린 조건이 계획에 이미 없었는지 SQL로 옮기면서 사라졌는지 찾아볼 수 있었다.

실제 예비 실행의 bang-001을 읽으며 계획이 SQL의 어디로 가는지 표시했다. “주문과 결제를 주문 번호로 연결하고, 2017년에 구매해 배송 완료된 주문의 결제 수단별 합계를 구한다”는 계획이 각각 JOIN, 기간과 상태를 거르는 WHERE, GROUP BY와 SUM으로 이어졌다. 이 문항은 E0도 맞혔지만, 계획과 SQL을 대조하는 방법을 배울 수 있었다.

공부할 때는 Plan-and-Solve의 ‘계획 뒤 풀이’, Least-to-Most의 ‘앞 하위 문제의 답을 다음에 사용’, DIN-SQL의 ‘스키마 연결·분해·생성·수정’을 구분했다. 내가 맡은 비교에서는 그중 풀이 계획을 한 번 추가하는 변화부터 다뤘다. Plan-and-Solve · Least-to-Most · DIN-SQL

후보 20문항을 돌려 보고, 다음에 확인할 것을 바꿨다

10월 27일에는 Sol로 확정 전 후보 20문항을 돌려 봤다. E0와 A3 모두 17개를 맞혔다. bcds-002는 E0에서 시간 초과했고 A3에서 통과했다. 반대로 ksj-001은 E0에서 통과하고 A3에서 시간 초과했다. 이 기록에서 계획이 시간 초과를 줄인다는 방향은 뚜렷하지 않았다. 다음 비교에서는 풀이 계획이 조건이나 집계 단위를 빠뜨리는 오류를 줄이는지를 보기로 했다.

10월 30일에는 확정된 Olist v0.2의 같은 30문항을 Luna로 E0와 A3 각 한 번 실행했다. SQL 생성 지시문과 10초 실행 제한은 같았다. 정답은 둘 다 23/30이었고, 모델 호출은 30회에서 60회로 늘었다. A3에서 새로 맞힌 세 문항 중에는 반환 열 개수가 달랐던 bird-012가 있었다. 새로 틀린 세 문항 중 kmk-001은 한 해에만 등장한 카테고리를 포함하는 조건이 계획에서 빠져, 기대한 485행 대신 392행을 반환했다.

어떤 문항은 계획을 붙였을 때 나아졌고 어떤 문항은 계획 단계부터 기준이 빠졌다. 다음 주에는 같은 조건을 반복해 그 차이가 다시 나타나는지 확인하고, 계획 호출과 SQL 지시문을 따로 비교했다.
