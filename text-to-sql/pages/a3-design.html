E0에서 무엇을 바꿀까? 모델과 방법을 시험하고 A3를 고르기까지

작업 기록 · 2026년 10월 26–30일

Sonnet과 로컬 Qwen은 Olist 예비 평가에서 둘 다 네 문항 중 두 개를 맞혔다. 그런데 같은 재구매 문항 hjy-001에서 Sonnet의 SQL은 시간 초과했고 Qwen의 SQL은 SQLite 문법 오류로 멈췄다. 점수만 보면 같은 실패였지만, 한쪽은 쿼리가 왜 오래 걸렸는지 봐야 했고 다른 쪽은 SQLite에서 실행할 수 있는 구문부터 확인해야 했다.

3주차에는 이 차이를 보면서 내가 맡을 실험을 골랐다. 팀의 기본 실행인 E0는 질문, 문항 조건, 전체 스키마를 모델에 주고 SQL을 한 번 생성한 뒤 SQLite에서 실행해 정답과 비교한다. 2주차에 만든 문항을 가지고 모델과 추론 강도를 바꿔 보고, 예제나 데이터 사전처럼 모델에 전달하는 정보도 바꿔 봤다. 그중 내가 더 살펴볼 문제는 기준이 주어졌을 때 모델이 그 기준을 어떤 순서로 적용하는가였다.

모델을 바꿀까, 모델에게 주는 정보를 바꿀까?

팀의 A1~B4를 보니 손댈 수 있는 곳이 두 군데였다. 모델이 필요한 정보를 알고도 SQL을 잘못 쓰면 모델이나 생성 절차를 바꿔 볼 수 있다. 테이블의 뜻이나 실제 값을 몰라서 틀리면, 그 정보를 먼저 주는 쪽이 맞다. 같은 문제를 놓고 예제나 설명을 더했을 때, 앞에서 본 실패가 사라지는지부터 살폈다. 팀 실험에서는 각자 맡은 조건 하나를 E0와 비교하는 방식이었다.

A1~B4의 변경 지점과 네 문항 예비 결과
실험 E0에서 바꾸는 지점 10월 26일 Olist v0.1 예비 정답
A1 · 모델 교체 SQL을 생성하는 모델을 바꾼다 3/4
A2 · 예제 질문과 SQL 예제를 입력에 붙인다 2/4
A3 · 문제 쪼개기 SQL을 쓰기 전에 풀이 계획을 한 번 생성한다 3/4
A4 · 여러 후보 SQL 후보 여러 개를 만들고 실행 결과를 보고 고른다 실행 기록 없음
B1 · 데이터 사전 테이블과 열의 의미를 설명한다 3/4
B2 · 값 예시 주문 상태나 결제 수단 같은 실제 값의 예를 준다 2/4
B3 · 지표 정의 매출, 신규 고객, 재주문의 계산 기준을 설명한다 2/4
B4 · 검색 질문과 관련된 사전 조각을 찾아 붙인다 2/4

A1은 Luna로 바꿔 실행했고, A2·A3와 B1~B4는 Sol로 실행했다. 당시 공유 E0는 Sol에서 3/4였다. 예비 실행의 Codex CLI는 0.163.0, 공유 E0의 CLI는 0.160.0이었다. 각 방법의 기록은 네 문항을 한 번씩 돌려 본 관찰이다. A4는 별도의 API 기준선이 필요한 선택지로 검토했다.

A2는 예제를 붙이고 B2·B3·B4는 데이터에 관한 정보를 더하는 서로 다른 시도였다. 그래도 이 네 시도에서 hjy-001은 모두 SQL 시간 초과로 실패했다. 한 번씩 돌린 점수를 순위로 읽기 전에, 추가 정보가 질문의 기준을 더 분명히 했는지와 생성 SQL이 제한 시간 안에 실행됐는지를 구분해야 했다.

추론을 더 오래 하면 같은 문항을 맞힐까?

설명을 더해도 시간 초과가 남았다. 그럼 모델을 바꾸거나 추론 강도를 높이면 생성되는 SQL이 달라질까? 같은 Olist v0.1 SQL 네 문항에 Luna의 추론 설정을 바꿔 넣었고, Claude CLI의 Haiku와 Sonnet, Docker의 Qwen2.5-Coder 7B에서도 결과를 확인했다.

모델별 정답과 SQLite 실행 성공
실행 정답 실행 성공
공유 E0 · Codex Sol 3/4 4/4
Codex Luna · low / medium / high 3/4 · 3/4 · 2/4 모두 4/4
Claude CLI · Haiku 4/4 4/4
Claude CLI · Sonnet 2/4 3/4
Docker · Qwen2.5-Coder 7B 2/4 3/4

Haiku는 네 문항을 모두 맞혔고, Luna는 추론 강도를 올렸을 때 오히려 정답이 3개에서 2개로 줄어든 실행도 있었다. 네 문항에서는 하나만 바뀌어도 점수가 25%p 움직인다. 실행 도구와 제공자 설정도 달랐다. 이 표로 모델을 고르기보다 결과가 달라진 문항에서 무엇이 달랐는지 읽었다.

데이터 사전을 시험한 뒤, 풀이 순서를 살펴보기로 했다

10월 26일 진행 계획에서는 데이터 사전이 먼저 살펴볼 후보였다. 앞선 과제에서 customer_id와 customer_unique_id, 주문과 상품·결제의 행 단위를 혼동하면 결과가 달라지는 것을 확인했기 때문이다. 팀에서 B1을 맡은 사람이 있어, 나는 테이블과 열의 설명에 한 행의 뜻과 조인 규칙을 포함한 B1-b도 따로 돌렸다. 실제 상태 값 목록과 내 평가 문항의 함정을 알려 주는 문장은 덜어 냈다.

B1-b는 3/4로 공유 E0와 같은 문항을 맞혔다. 남은 hjy-002는 집계 수치는 맞았지만 카테고리명이 포르투갈어였다. 기대 결과는 영어였고, 모델 입력에는 영어로 반환하라는 조건이 없었다. 이 경우에는 테이블을 더 자세히 설명하는 것보다 채점에 쓰는 출력 언어를 질문에서 확인할 필요가 있었다.

같은 주에 팀 리뷰를 받은 재주문율과 신규·기존 고객 결제액 문항도 보완했다. 재주문율 문항은 두 해 모두 수령 후 30일을 관찰할 수 있도록 3~7월 수령으로 범위를 맞췄다. 결제액 문항은 전체 배송 완료 이력에서 고객의 첫 구매를 찾고, 결제액은 2018년 1분기 주문만 합산하도록 정리했다. 1분기로 먼저 자르면 2017년 구매 기록이 사라져 기존 고객도 신규처럼 보일 수 있었다.

두 사례를 나란히 놓으니 시험할 변경이 구체적이었다. 카테고리명은 질문과 채점의 기준부터 맞춰야 한다. 신규 고객 문항에서는 기준을 알려 줘도 1분기 필터를 먼저 적용하면 답이 달라진다. 팀에서 데이터 사전 실험을 맡은 사람이 있었고, 나는 후자의 문제를 다룰 수 있는 A3를 골랐다. 먼저 계획을 쓰게 하면 빠진 단계나 잘못된 순서를 SQL을 실행하기 전에 확인할 단서가 생긴다.

10월 27일, A3로 비교할 두 경로를 발표했다

내가 맡은 A3에서는 모델이 먼저 사용할 테이블, 조인 키, 필터, 집계 단위와 계산식, 정렬·개수 제한을 글로 적는다. 두 번째 호출에서 원래 질문·문항 조건·스키마와 그 계획을 받아 SQL 하나를 만든다. 계획과 SQL이 각각 남기 때문에, 빠뜨린 조건이 계획에 이미 없었는지 SQL로 옮기면서 사라졌는지 찾아볼 수 있었다.

실제 예비 실행의 bang-001을 읽으며 계획이 SQL의 어디로 가는지 표시했다. “주문과 결제를 주문 번호로 연결하고, 2017년에 구매해 배송 완료된 주문의 결제 수단별 합계를 구한다”는 계획이 각각 JOIN, 기간과 상태를 거르는 WHERE, GROUP BY와 SUM으로 이어졌다. 이 문항은 E0도 맞혔지만, 계획과 SQL을 대조하는 방법을 배울 수 있었다.

공부할 때는 Plan-and-Solve의 ‘계획 뒤 풀이’, Least-to-Most의 ‘앞 하위 문제의 답을 다음에 사용’, DIN-SQL의 ‘스키마 연결·분해·생성·수정’을 구분했다. 내가 맡은 비교에서는 그중 풀이 계획을 한 번 추가하는 변화부터 다뤘다. Plan-and-Solve · Least-to-Most · DIN-SQL

후보 20문항을 돌려 보고, 다음에 확인할 것을 바꿨다

10월 27일에는 Sol로 확정 전 후보 20문항을 돌려 봤다. E0와 A3 모두 17개를 맞혔다. bcds-002는 E0에서 시간 초과했고 A3에서 통과했다. 반대로 ksj-001은 E0에서 통과하고 A3에서 시간 초과했다. 이 기록에서 계획이 시간 초과를 줄인다는 방향은 뚜렷하지 않았다. 다음 비교에서는 풀이 계획이 조건이나 집계 단위를 빠뜨리는 오류를 줄이는지를 보기로 했다.

이 20문항은 A3를 맡기까지 살펴본 후보 평가셋이다. 이후 확정된 Olist v0.2 30문항으로 넘어가면서 10월 30일에 Luna로 E0와 A3를 각 한 번 실행했다. 양쪽은 같은 SQL 생성 지시문과 10초 실행 제한으로 각각 23/30을 맞혔다. 이때부터 본격적으로 다룬 문제는 어떤 계획이 더 좋아 보이느냐보다, 한 번 달라진 문항이 같은 조건에서 다시 실행해도 같은 방향으로 바뀌느냐였다.
