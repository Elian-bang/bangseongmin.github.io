A3를 더 깊게 파보기 · Olist 49문항과 BIRD 500문항

작업 기록 · 2026년 11월 5–10일

판매자별 매출을 물었을 때 SQL을 바로 쓴 쪽은 세 번 모두 판매자 ID를 빠뜨렸다. 결과에 필요한 열을 먼저 적게 한 쪽은 세 번 모두 맞혔다. 그런데 같은 방식이 배송비를 묻는 문항에서는 집계할 주문의 범위를 좁혀 세 번 중 두 번을 틀렸다.

4주차에 계획 단계만의 효과를 판단하지 못한 뒤, 이번에는 질문을 두 개로 나눴다. 계획에 무엇을 적게 해야 하고, 언제 계획을 써야 할까? 첫 질문은 지시를 하나씩 바꿔 살폈다. 두 번째는 Olist와 BIRD에서 계획 호출을 줄였을 때 정답 수가 어떻게 달라지는지 시험했다.

일곱 열을 반환한 SQL에서 출력 지시 한 줄을 골랐다

js-002는 7월 15일의 불만 리뷰 비율과 전일·전월·전년 대비 증감폭을 묻는다. 한 실행에서 SQL은 증감폭을 구하는 데 쓴 비교일 비율까지 결과에 포함해 일곱 열을 반환했다. 채점기가 기대한 결과는 기준일 한 행과 네 열이었다. 다섯 항목을 한꺼번에 지시하면 어느 항목이 이 오류에 영향을 주는지 가르기 어려웠다. 그래서 최종 출력 항목만 떼어 냈다.

A와 B는 질문·문항 조건·스키마를 읽고 먼저 계획을 썼다. B의 첫 호출에만 “한 행이 나타내는 의미와 필요한 출력 항목을 적는다”를 덧붙였다. 두 번째 호출은 양쪽 모두 원래 입력과 각자의 계획을 받아 같은 지시문으로 SQL을 작성했다. Olist v0.3의 같은 49문항을 조건마다 세 번 풀고, 전체 정답과 출력 형태를 함께 봤다.

전체 정답은 A 117/147, B 121/147이었다. 하지만 js-002와 함께 확인하기로 한 bird-012·bird-016은 두 조건 모두 각각 3/3이었다. 전체 시도에서도 열 개수 오류는 양쪽 모두 0건, 행 개수 오류는 각각 1건이었다. 두 번 이상 더 맞힌 문항은 2개, 두 번 이상 덜 맞힌 문항은 1개로 차이는 +1이었다. 사전에 정한 +2 기준과 목표 오류 감소를 함께 충족하지 못해 한 줄의 효과는 판단을 보류했다.

출력 지시 비교의 실행 조건과 회차별 결과

같은 SQLite DB와 스키마, gpt-6-luna의 medium 설정, Codex CLI 0.166.0을 사용했다. SQL 실행 한도는 10초와 1,000행이었다. 실행 순서는 A→B, B→A, A→B였고, 첫 호출의 문항별 입력 해시와 두 번째 호출의 SQL 지시문 해시가 양쪽에서 일치했다.

하위 질문마다 쓸 테이블과 열을 적으면 더 잘 맞힐까?

Plan-and-Solve에서 풀이 전에 계획을 세우는 순서를, DIN-SQL에서 스키마 연결과 문제 분해의 역할을 살폈다. Tai 등의 논문에서 눈여겨본 건 하위 질문 옆에 그 질문을 푸는 데 필요한 테이블과 열을 적는 방식이었다. 예를 들어 전년 대비 결제액을 구한다면, “두 기간의 결제액을 각각 어떻게 구할까?”라는 하위 질문 옆에 구매 시각을 담은 orders.order_purchase_timestamp와 결제 금액을 담은 order_payments.payment_value를 적을 수 있다. Plan-and-Solve · DIN-SQL · QDecomp와 InterCOL

자유 계획에 하위 질문을 쓰게 하면 정답이 늘까? 거기에 테이블과 열까지 적게 하면 한 번 더 나아질까? A에서는 모델이 계획의 항목을 정한다. D에서는 자유 계획 지시에 하위 질문과 각 질문의 역할을 적으라는 문장을 더한다. E에서는 D의 지시를 그대로 두고 각 하위 질문에 필요한 테이블과 열을 쓰라는 문장만 더한다. 같은 평가셋 안에서 질문·스키마·모델·SQL 생성 지시문을 고정했다. A와 D는 질문 분해를, D와 E는 테이블·열을 명시하는 차이를 보기 위한 짝이다.

Olist v0.3의 같은 49문항을 조건마다 세 번 풀었을 때, 자유 계획 A의 114/147은 하위 질문을 적는 D에서 109/147로 줄었다. 테이블과 열까지 적은 E에서는 124/147로 올랐다. 다른 DB에서도 이 순서가 나올까? BIRD Mini-Dev SQLite 500문항에서 조건당 한 번 생성한 SQL을 공통 채점기로 비교하니, A는 246/500, D는 233/500, E는 216/500이었다. Olist에서 정답을 더 낸 지시가 BIRD에서는 같은 방향으로 움직이지 않았다. BIRD Mini-Dev 공식 저장소

각 실험은 같은 49문항을 세 번씩 풀고 해당 실험의 자유 계획 실행과 짝을 맞췄다. 하위 질문만 추가한 별도 실행에서는 세 회차 가운데 두 회차에서 정답이 늘고 한 회차에서 줄었다. 다섯 가지 계획 방식을 함께 비교했을 때는 D의 합계가 A보다 낮았다.

정답을 더 낸 E와 더 꾸준했던 B 중 무엇을 이어서 쓸까?

다섯 방식의 본 실험에는 출력만 적게 한 B와 기존 다섯 항목을 한꺼번에 적게 한 C도 넣었다. Olist에서 E의 전체 정답 수가 가장 높았지만, 같은 문제를 세 번 모두 맞힌 문항 수로 보면 순서가 달랐다.

Olist에서 E는 B보다 전체 정답을 두 건 더 냈고, B는 세 번 모두 맞힌 문항이 E보다 두 개 더 많았다. Olist에서 이어갈 실험이라면 같은 질문을 다시 풀 때도 맞히는 쪽을 써 보자고 판단했다. 결과를 본 뒤 B를 골랐다.

BIRD 표는 최초 실행의 SQL을 다시 채점한 값이다. 처음에는 card_games DB를 여는 오류가 생겼다. SQL을 그대로 두고 공통 읽기 전용 경로에서 SQL당 30초 제한으로 다시 채점하자 DB 열기 오류가 0건이 됐다.

모든 질문에서 계획을 쓰면 호출이 두 배 가까이 든다

같은 CLI를 쓴 Olist 후속 비교에서, 바로 SQL을 작성한 E0와 B의 정답은 각각 122/147이었다. 호출은 147회와 294회였다. bird-012에서는 B가 판매자 ID를 반환해 0/3 → 3/3이 됐다. hard-017에서는 B가 두 회차에서 배송일이 있는 주문으로 대상을 좁혀 3/3 → 1/3이 됐다. BIRD 500문항을 세 번 푼 별도 후속 비교에서는 E0 669/1,500, B 715/1,500이었고 호출은 1,500회에서 2,998회로 늘었다. 이 후속 비교는 E0와 B를 세 번씩 실행한 결과다. 앞 표의 BIRD 열은 A~E에서 조건당 한 번 생성한 SQL을 다시 채점한 결과다.

그래서 질문에 ‘전년’이나 ‘previous year’처럼 비교·재구매를 드러내는 표현이 있을 때만 B를 쓰는 규칙을 시험했다. 이미 실행한 E0와 B의 문항별 결과에서 규칙이 고른 쪽을 합산했다. 항상 B를 쓰는 경우보다 호출은 Olist 294회 → 192회, BIRD 2,998회 → 1,557회로 줄었다. 정답도 각각 122/147 → 120/147, 715/1,500 → 676/1,500으로 줄었다.

SQL을 쓰는 두 번째 호출에 넘기는 스키마도 줄여 봤다. B의 계획을 유지하고 필요한 테이블 정의만 선별한 결과, BIRD에서 SQL 생성 입력 토큰은 약 9.5% 줄었지만 정답도 715/1,500 → 656/1,500으로 줄었다. 두 실험에서 비용을 줄인 만큼 어떤 문항의 정답을 잃는지까지 기록했다.

시간 초과가 확인된 SQL에 실행 계획을 건넸다

질문 표현으로 계획 호출을 선별하는 실험과 별도로, 첫 SQL이 시간 초과했을 때만 모델을 다시 불렀다. 4주차에 분류한 오답 34건 중 22건이 시간 초과였기 때문이다. 기본 재시도는 실패 SQL과 오류 메시지를 모델에 줬다. 단서를 준 재시도는 같은 입력에 EXPLAIN QUERY PLAN에서 추린 한 줄을 추가했다. 풀이 계획이 무엇을 세고 반환할지 정한다면, 여기서 쓴 SQLite 실행 계획은 DB가 그 SQL을 어떻게 처리하는지 보여 준다. SQLite 실행 계획 문서

Olist 첫 회차의 hjy-001에서 처음 만든 SQL은 EXISTS 안에서 바깥 쿼리의 고객과 첫 구매 시각을 참조했다. 실행 계획에는 CORRELATED SCALAR SUBQUERY 5가 있었다. 기본 재시도에서 만든 SQL도 시간 초과했다. 단서를 받은 모델은 EXISTS를 조인으로 바꿔 재구매 고객을 별도 중간 결과로 만들었다. 실행은 끝났지만, 정답 한 행 대신 37행을 반환해 오답이었다. 시간 초과에서 벗어난 건수와 정답을 복구한 건수를 따로 센 이유다.

기본 재시도에서 실행 계획 단서를 더한 재시도로 바꾸자, 전체 정답은 Olist 125/147 → 127/147, BIRD 729/1,500 → 732/1,500이었다. 다시 시간 초과한 건은 각각 9건 → 5건, 5건 → 1건으로 줄었다. 두 조건에 같은 재시도 횟수를 썼지만, 재시도 자체는 이미 한 번 시간 초과를 기다린 뒤에 모델을 다시 부르는 선택이다. 다음에는 계획 없이 만든 E0의 같은 첫 SQL로 두 재시도를 비교해, 정답과 시간 초과의 차이가 다시 나오는지 보고 추가 토큰과 시간도 기록하기로 했다.
