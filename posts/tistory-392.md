## 인덱스를 다룰 때 주의해야 할 점

---

인덱스를 다룰 때 주의해야할 점은 크게 3가지로 나눌 수 있습니다.

1. 인덱스 필드 가공
2. 복합 인덱스
3. 하나의 쿼리에는 하나의 인덱스만

### 인덱스 필드 가공

---

인덱스 필드를 가공하게 되면 인덱스가 동작하지 않게 됩니다.

```sql
// 연산하는 경우
SELECT *
FROM Member
WHERE age * 10 = 1

// 타입을 잘못 선언한 경우
SELECT *
FROM Member
WHERE age = '1'
```

첫 번째 쿼리는 해당하는 데이터가 존재한다고 하더라도 age에 값을 곱하여 칼럼 값을 변경시키기 때문에 인덱스가 탈 수 없습니다.

[인덱스의 동작원리](tistory-389.html#toc-%EC%9D%B8%EB%8D%B1%EC%8A%A4%EC%9D%98%20%EA%B8%B0%EB%B3%B8%20%EB%8F%99%EC%9E%91=)를 보면 B+Tree 형태로 자료구조가 구현되어 있는데 B+Tree에 저장되어있는 Key 값으로만 인덱스로만 인덱스 검색이 가능합니다. 그래서 연산이 되면 달라지기 때문에 인덱스를 탈 수가 없습니다. 

두 번째 쿼리를 보면 알 수 있듯이 타입을 잘못 선언하는 경우가 있습니다. age는 int 타입인데 문자열로 넘겨주면 index를 탈 수 없게 됩니다. B+Tree에 저장되어있는 Key의 타입은 int이고 Query에 설정한 데이터는 String 이기 때문에 B+Tree를 탈 수 없게 됩니다. 

> 인덱스 필드에 가공이 들어가게 되면 인덱스를 탈 수 없다.

### 복합 인덱스

---

과일 인덱스에 원산지 인덱스를 합쳐서 설정한 것과 같이 복합 인덱스를 설정할 수 있습니다.

![본문 이미지](../assets/tistory/de9cf9922a973036574157ec.png)

복합 인덱스를 설정하면 가장 먼저 과일 순서대로 정렬되게 됩니다.

과일 순으로 정렬한 다음에 만약 과일이 같다면 원산지 순으로 정렬하게 됩니다. 

복합 인덱스를 설정할 때 위와 같이 그림을 그리면 더 쉽게 이해할 수 있습니다. 

복합 인덱스를 설정할 때 중요한 것은 데이터의 분포도입니다. 데이터의 분포도가 높은 것을 복합 인덱스의 앞자리에 두는 것이 좋습니다. 

### 하나의 쿼리에는 하나의 인덱스

---

* 하나의 쿼리에는 하나의 인덱스만 탄다.
* 여러 인덱스 테이블을 동시에 탐색하지 않습니다(index merge hint를 사용하면 가능)

그렇기 때문에 **WHERE**, **ORDER BY,** **GROUP BY**를 혼합해서 사용할 때에는 인덱스를 잘 고려해야합니다.

WHERE 문에 설정한 필드를 기준으로 INDEX를 타면 ORDER BY는 타지 못하면 가져온 데이터를 다시 정렬해야 합니다.

### 정리

---

* **의도대로 인덱스가 동작하지 않을 수 있다. (Explain 키워드를 통해 확인 가능)**
* **인덱스도 비용이다 -> 쓰기를 희생하고 조회 성능을 얻는 것**
* **꼭 인덱스로만 해결할 수 있는 문제인가?**  
  인덱스를 해결하는 것이 간단하긴 하지만 조회 조건(특히 정렬)을 생각보다 많이 바뀌기 때문에 어느 순간에는 인덱스로 해결할 수 없는 순간이 올 것이다. 해결방법으로 별도의 테이블을 사용할 수 있고, 읽기와 쓰기를 분리할 수 있고 캐싱할 수도 있습니다.
