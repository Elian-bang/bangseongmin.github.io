## A is B but B is not A

---

저번 주부터 이전에 만들었던 기능을 분리하기 시작해서 오늘 마무리가 되어 해당 기능을 수행하는 Batch 코드의 성능 최적화를 하기 시작했다.

기능이 덧붙여지고 덧붙여지고 기능이 변경되기 전에 데이터를 처리해주기 위한 코드가 함께 있는 코드라서 더 깔끔하게 관리하기 위해 먼저 코드를 정리하였습니다.

변경 후, 스케쥴러 주기에 적정한 양의 데이터 수를 측정하기 위해 더미 데이터를 삽입하여 테스트를 진행하였습니다.

![본문 이미지](../assets/tistory/b633147bf391fc384968c721.gif)

중복된 로직을 제거하고 테스트를 했는데... 예상보다 성능이 나오지 않았습니다. 그래서 중복된 코드가 더 있을 것이라는 생각이 들어 코드를 찾아서 중복된 코드와 반복적으로 수행되는 쿼리를 줄였습니다.

생각했던 것보다 훨씬 느린 속도를 경험할 수 있었습니다...

그래서 이전에 공부한 경험을 바탕으로 Insert와 update를 개별적으로 하지 않고 Bulk로 한번에 처리되도록 변경하였습니다!!

![본문 이미지](../assets/tistory/a612e6ded2acede1461f5031.gif)

그런데?? 성능이 더 늦게 나와서 뭐지..? 하고 몇 번더 동일한 테스트를 진행했습니다.

처음에 나온 성능이 이상한 것이였고 조금 줄긴 했습니다... 하하 이게 내 최선인가라는 생각이 들었습니다...

이전 Batch 코드와 비교해서 어느정도 성능이 최적화된 것인지 확인해보기 위해 이전 코드를 기준으로 테스트를 했는데... 

![본문 이미지](../assets/tistory/9ded92f571a9601367ec1c40.gif)

더 빠른 성능을 보여주는 일을 발견할 수 있었습니다.. 하하하하ㅏ하하하하ㅏ하하하

분명 나는 코드의 중복을 줄였고, 오히려 쿼리의 양도 줄었는데... 뭐지??? 라는 생각을 하면서 코드를 다시 롤백시켰습니다.... 

그리고 원래 코드의 중복을 제거하여 조금 더 최적화시켰습니다...

Bulk로 삽입 및 업데이트가 더 빠를 수 있으나 인덱스가 많이 걸려있을 경우, 더 느릴 수 있을 것이라는 생각이 들었습니다.

흠.. 너무 부족해!! 더 빨리 성장해야지~~
